# Stream Keepr

Event management and streaming overlay system for competitive gaming tournaments
(MTG, One Piece).

- **Event management**: tournament Events with game-specific settings.
- **Players and Matches**: player records, deck lists, pairings, results, best-of
  series, standings.
- **Streaming overlays**: card displays, deck views, match info, Feature Match
  Overlay, and Broadcast Graphics Screens rendered to OBS browser sources.
- **Melee integration**: sync tournament data from Melee.
- **Realtime**: live sync across connected clients via Ably.

This README is the single guide for developing, testing, deploying, and
operating Stream Keepr. The other docs:

| File           | Holds                                                                |
| -------------- | -------------------------------------------------------------------- |
| `CONTEXT.md`   | The domain glossary. Use its terms in code, tests, issues, and docs. |
| `DECISIONS.md` | Settled architecture decisions and why (cited as ADR-NNNN).          |
| `AGENTS.md`    | Rules for coding agents working in this repo.                        |
| `CHANGELOG.md` | Generated by release-please; never edit by hand.                     |

## Stack and layout

Nuxt 4 SPA (`ssr: false`), Vue 3, Pinia, Nuxt UI, Tailwind; Nitro on Cloudflare
Workers via NuxtHub; D1 (SQLite) with Drizzle; R2 for graphics bytes; Ably for
realtime; Better Auth for accounts.

```text
app/        Frontend: pages, components, stores, composables
server/     Backend: API routes, modules, services, DB schema and migrations
shared/     Types and utilities shared by app and server
workers/    The silent-video validator Worker + Container
scripts/    Worker guards, acceptance harnesses, deploy helpers
build/      Nuxt build-time modules and local-configuration checks
test/       unit, nuxt, integration suites
```

## Setup

Use Node 24 LTS (24.11+; `.node-version` pins CI's exact version) and the pnpm
version pinned in `package.json`.

```bash
pnpm install
cp .env.example .env   # then fill in the values, see below
```

### Local configuration

`.env` at the repository root is the only local configuration file. It reaches
every way the app runs locally:

- `pnpm dev` and the test suites load it into `process.env`. A dev server
  missing required names warns once at boot rather than answering 503 per
  surface.
- `pnpm preview` copies it to `.output/server/.env`, because Wrangler resolves
  `.env` relative to its config file. Edit the root copy; the staged one is
  overwritten on every preview.
- Local acceptance harnesses read it directly and refuse to start if it lacks
  `NUXT_SCREEN_OUTPUT_CAPABILITY_SIGNING_KEY`, `NUXT_BETTER_AUTH_SECRET`, or
  `NUXT_ADMIN_BOOTSTRAP_TOKEN`.

`.env` is gitignored, so **a new git worktree starts without it**. Copy it in
when you create one (a worktree also needs its own `pnpm install`):

```bash
cp .env .claude/worktrees/<name>/
```

Without it, dev answers 503 from the admin and Screen Output surfaces, and the
two realtime integration tests skip. That is a configuration gap, not a
failure on `main`.

| Name                                             | Purpose                                                                                                                    |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| `NUXT_BETTER_AUTH_SECRET`                        | Signs sessions. Unset: sign-in and every authenticated route answer 503.                                                   |
| `NUXT_ADMIN_BOOTSTRAP_TOKEN`                     | Arms the first-admin route. Locally, leave it set; it is how a fresh checkout and the local harnesses get an account.      |
| `NUXT_GRAPHICS_ADMIN_TOKEN`                      | Graphics Administrator token for `/admin/**` pages and `/api/admin/**` routes.                                             |
| `NUXT_SCREEN_OUTPUT_CAPABILITY_SIGNING_KEY`      | 32-byte base64 HMAC key for Screen Output asset capabilities.                                                              |
| `NUXT_ABLY_API_KEY`                              | Ably key. Optional for tests: leave it empty rather than fake. A fake key makes one realtime test pass and the other fail. |
| `NUXT_MELEE_CREDENTIAL_ENCRYPTION_KEY`           | 32-byte base64 key encrypting Melee client secrets (AES-256-GCM).                                                          |
| `NUXT_MELEE_CREDENTIAL_ENCRYPTION_KEY_VERSION`   | Non-empty version label for the active key.                                                                                |
| `NUXT_MELEE_CREDENTIAL_ENCRYPTION_PREVIOUS_KEYS` | Optional JSON `{"<version>":"<key>"}` of retired keys still needed to decrypt during rotation.                             |

Generate keys and secrets with `openssl rand -base64 32`. A deployed Worker
reads no file; there these are Worker secrets (see [Worker secrets](#worker-secrets)).

## Development

| Launcher                | Serves                 | Auth                 |
| ----------------------- | ---------------------- | -------------------- |
| `pnpm dev`              | loopback               | Better Auth          |
| `pnpm dev:bypass`       | loopback               | Local Developer User |
| `pnpm dev:local`        | the LAN (`0.0.0.0`)    | Better Auth          |
| `pnpm dev:local:bypass` | the LAN (`0.0.0.0`)    | Local Developer User |
| `pnpm preview`          | loopback, built Worker | Better Auth          |
| `pnpm preview:bypass`   | loopback, built Worker | Local Developer User |

`pnpm preview` builds, applies migrations to an ignored local D1 store under
`.wrangler/state/built-worker`, and runs the generated Worker under local
workerd. It never touches a remote database.

Stop dev servers with Ctrl-C (SIGINT) or SIGTERM. A server killed with SIGKILL
or SIGHUP strands its `workerd` process, which then holds memory and sqlite
locks. `pnpm dev`, `pnpm preview`, their `:bypass` variants, `pnpm
worker:smoke`, and the integration suite reap orphans on start; `pnpm reap`
does it on demand and only ever kills `workerd` whose parent is gone.

### Local auth bypass

The `:bypass` launchers set `STREAM_KEEPR_LOCAL_AUTH_BYPASS=true` on their own
command line. **That is the only place the name is written.** Never put it in
`.env`, `.env.example`, `wrangler.jsonc`, CI, or a Worker var. Nothing needs it:
builds, tests, `pnpm verify`, and CI behave identically without it. The server
compares it to the exact string `true` and infers nothing from `NODE_ENV`,
hostnames, or bindings. `pnpm worker:dry-run` fails if generated deploy config
carries it. `pnpm preview:bypass` stages it into `.output/server/.env`, which
every `nuxt build` wipes, so a deploy cannot pick it up.

Under a bypass:

- `NUXT_BETTER_AUTH_SECRET` and `NUXT_ADMIN_BOOTSTRAP_TOKEN` may be blank.
- Protected pages open as the stable **Local Developer User**. Each browser still
  gets its own Session, so Graphics Authoring Leases tell concurrent editors
  apart. The shell shows that identity and has no sign-out.
- Startup warns that authentication is bypassed.
- It does **not** cover the Graphics Administrator token, Screen Output
  capabilities, or any other configuration.

**`pnpm dev:local:bypass` gives every machine that can reach yours
unauthenticated access.** It exists for testing from a phone, tablet, or the
broadcast machine, where sign-in cannot work because a LAN address is not in
`AUTH_ALLOWED_HOSTS`. Use it only on a trusted network and stop it when done.
Binding any other bypassed launcher off loopback carries the same exposure
(ADR-0017, ADR-0018).

`pnpm verify` exists for its tail. `worker:dry-run` checks the upload bundle
statically; `worker:smoke` runs it under local workerd with production-shaped
requests. Together they catch bundles that pass on Node and break on workerd
(#302). Run it whenever a change touches dependencies, bundling,
`nuxt.config.ts`, or server code.

How `pnpm verify` runs:

- **Cheap gates first.** `nuxt prepare`, then lint, typecheck, and the unit and
  Nuxt suites; the build runs beside them. The server-backed suites and browser
  gates start only once those pass, so a lint or type error arrives in seconds.
- **Each gate logs to `node_modules/.cache/verify/<gate>.log`.** The terminal
  shows one line per gate and the tail of the first failure.
- **Lint and typecheck are cached** (`node_modules/.cache/eslint/`,
  `node_modules/.cache/tsc/`), so an unchanged tree lints and typechecks in
  seconds. The ESLint cache is per file, so a type-aware rule can miss a finding
  in an unchanged file that a changed file's types caused; CI starts cold and
  catches it. Delete the cache directory to reproduce CI exactly.
- **Only `nuxt prepare` writes `.nuxt`.** The root tsconfig extends it, so every
  other gate reads it; the Nuxt suite, the servers and `verify`'s build each use
  their own build directory. Keep it that way when adding a gate.

CI (`.github/workflows/ci.yml`) runs the same gates as `pnpm verify` on every PR,
split across two jobs. It skips docs-only PRs and does not re-run on merge.
Realtime integration tests self-skip in CI: no Ably key is configured there, by
decision (#189). The suites in the table above that need a running preview,
Docker, Safari, or a real store stay local. Other vitest modes work directly,
e.g. `pnpm exec vitest --ui`.

Gotchas:

- **Run integration suites one at a time.** Concurrent runs, or a loaded
  machine, make every result meaningless. A cascade of `ECONNREFUSED` or
  "session cookie was not issued" with zero assertion failures means a
  `workerd` backend died, not that the code broke.
- **The integration suite runs several servers.** One `nuxt dev` per vitest
  worker, each over its own database under `.wrangler/state/integration-<n>`, so
  test files run in parallel but never two against one database. The default is
  a third of the CPU cores, at most four; set `STREAM_KEEPR_INTEGRATION_SERVERS`
  to change it (`1` is the old serial run). Each server's output is kept in
  `node_modules/.cache/integration-servers/`.
- **Nuxt-suite failures under load are often timing.** A 30s `setupNuxt`
  timeout shows skipped tests; 5s per-test timeouts show bimodal durations.
  Re-run the single file, then the suite with `--no-file-parallelism`, before
  believing a broad failure.
- **The Nuxt suite is selected by config**, not project:
  `vitest --config vitest.nuxt.config.ts`.
- **Local acceptance harnesses target `http://127.0.0.1:8787`**, whichever
  checkout is serving it, and provision real Events there. Set
  `STREAM_KEEPR_LOCAL_ACCEPTANCE_URL` to aim at your own preview.
- **Use `pnpm lint`**, not `npx eslint`, which resolves nothing locally and exits 0. ESLint also exits 0 on warnings, so read the output.

## Database

```bash
pnpm db:generate  # generate a migration from schema changes
pnpm db:migrate   # apply migrations
```

**Read every generated migration before committing it.** SQLite refuses
`ALTER TABLE … ADD COLUMN … NOT NULL` without a `DEFAULT`, but only when the
table has rows, so a missing default passes locally and fails on the first
replay against real data (#310). `pnpm db:generate` will not add one; you do.
If the new column has a unique index, a constant default collides, so backfill
per row between the `ALTER` and the `CREATE UNIQUE INDEX`
(`0007_serious_the_hunter.sql` is the worked example, using
`hex(randomblob(n))` or the row's primary key).
`test/unit/server/db/migrationJournalReplay.test.ts` replays the journal against
populated tables and catches this.

D1 records applied migrations **by name**, so editing an applied migration is a
no-op wherever it already ran and only changes future replays. Prefer repairing a
broken migration in place over adding a corrective one.

## Releases

release-please (`.github/workflows/release-please.yml`) versions from
conventional commits: `fix:` → patch, `feat:` → minor, `feat!:` or
`BREAKING CHANGE` → major. It keeps one rolling Release PR against `main`.
**Merging that PR is the release**: it tags `vX.Y.Z`, publishes a GitHub
Release, bumps `package.json`, and updates `CHANGELOG.md`. `main` is trunk;
there is no `develop` branch.

Requires Settings → Actions → General → **Allow GitHub Actions to create and
approve pull requests**. Release PRs do not trigger CI (default-token
limitation); wire a PAT before adding required status checks to `main`.

## Deploy

NuxtHub generates the deployable config at `.output/server/wrangler.json`.
`wrangler.jsonc` holds shared runtime policy (routes, R2, cron, service binding,
observability); D1 and KV bindings and their production IDs come from
`nuxt.config.ts`. Deploys use the repo-pinned Wrangler.

There is no separate staging environment: **production is the staging gate.**
The production hostname is `https://stream.keepr.digital`, attached as a
`custom_domain` route in `wrangler.jsonc`.

`pnpm deploy` runs, in order and stopping at the first failure:

1. `CLOUDFLARE_ENV=production pnpm build`. The variable reaches only the build.
   NuxtHub uses it to pick an `env.<name>` block, and none exists today; it is
   kept so named environments work if added.
2. `pnpm worker:dry-run`: bundles what Wrangler would upload into
   `.output/wrangler-dry-run/` and fails if it contains
   `new WebAssembly.Module(`, which a deployed Worker refuses (every JPEG/WebP
   ingestion would fail, #302). It also fails if the bypass name appears in
   generated config.
3. `pnpm worker:smoke` against that production build.
4. `pnpm db:migrate:remote`.
5. `wrangler deploy`.
6. `pnpm deploy:verify`: curls `GET /api/time` on the deployed Worker with
   retries. Set `STREAM_KEEPR_DEPLOY_HEALTH_URL` only to verify a different host.

Migration and promotion are separate Cloudflare operations, not one
transaction. Schedule incompatible schema changes for a maintenance window.

### Deploy from GitHub Actions

The **Deploy** workflow (`.github/workflows/deploy.yml`) is manual-only and runs
what `pnpm deploy` runs, but ships a **released tag**, never `main`'s HEAD:

- `version`: `latest` (default) or a tag like `v1.2.0`. Rollback is dispatching
  it with the previous tag.
- `d1_recovery_point`: must be typed `confirmed`.
- `validator`: `auto` (default) deploys the validator first only if
  `workers/silent-video-validator/` changed since the commit on the `production`
  git tag, which each successful deploy moves. `always` and `never` override.

It needs the `CLOUDFLARE_API_TOKEN` (Workers Scripts:Edit, D1:Edit, plus
Containers when deploying the validator) and `CLOUDFLARE_ACCOUNT_ID` repository
secrets. The acceptance gates and the "nothing on air" check stay with the
operator.

### Deploy day

Run these in order from a working checkout. Every gate provisions real Events
and assets in production and deletes them afterwards. A harness that dies
mid-run names the Event it left behind; delete it before rerunning.

1. **Pre-flight.** Nothing on air. Docker running. Secrets present
   (`pnpm exec wrangler secret list --name stream`). No leftover `workerd`
   (`pnpm reap`).
2. **Recovery point.** Build the production config, inspect pending
   migrations, and confirm a recent D1 Time Travel recovery point or export
   exists:

   ```bash
   CLOUDFLARE_ENV=production pnpm build
   pnpm db:migrations:list:remote
   ```

3. **Deploy.** Deploy the validator first when `workers/silent-video-validator/`
   changed, or on first deploy, so the service binding resolves:

   ```bash
   pnpm deploy:validator   # when the validator changed
   pnpm deploy
   ```

   If `deploy:verify` fails, stop and roll back: redeploy the previous Worker
   version (dashboard → Workers & Pages → Deployments, or
   `wrangler rollback`), then restore any applied migration from the recovery
   point.

4. **Set the harness variables:**

   | Variable                                    | Value                                                                             |
   | ------------------------------------------- | --------------------------------------------------------------------------------- |
   | `STREAM_KEEPR_BROWSER_ACCEPTANCE_URL`       | The installation to test. Falls back to `STREAM_KEEPR_DEPLOY_HEALTH_URL`.         |
   | `STREAM_KEEPR_ACCEPTANCE_OPERATOR_EMAIL`    | An existing operator account. `/api/**` denies by default, so gates must sign in. |
   | `STREAM_KEEPR_ACCEPTANCE_OPERATOR_PASSWORD` | That account's password.                                                          |

   A `:deployed` harness refuses to start without a URL rather than guessing.
   Without the operator pair it stops with `harness-operator-unavailable`.
   Setting `NUXT_ADMIN_BOOTSTRAP_TOKEN` in the shell also works if that secret is
   armed on the installation for the run.

5. **Run the gates.** Stop at the first failure.

   | #   | Command                                        | Proves                                                                                                    |
   | --- | ---------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
   | 1   | `pnpm test:validator:silent-video:deployed`    | The validator Workflow and Container accept H.264 MP4, VP9 WebM, and VP9-alpha WebM with correct posters. |
   | 2   | `pnpm test:delivery:graphics:deployed`         | Full and ranged delivery, ETags, caching, authorization, revocation, CORS/CSP, failure outcomes.          |
   | 3   | `pnpm test:browser:still-images:deployed`      | PNG, JPEG, and WebP decode in an OBS-like output.                                                         |
   | 4   | `pnpm test:browser:silent-video:deployed`      | MP4 and WebM play and seek; VP9 alpha keeps transparency on Chromium.                                     |
   | 5   | `pnpm test:browser:fonts:deployed`             | A library font revision is delivered, loads, and renders its glyphs.                                      |
   | 6   | `pnpm test:browser:safari-vp9-alpha:deployed`  | A Screen Output refuses Safari a VP9-alpha revision (409) while its session still opens.                  |
   | 7   | `pnpm test:delivery:graphics:package:deployed` | Template Package publication is atomic and its retry is idempotent.                                       |
   | 8   | [Fault injection](#fault-injection)            | Unavailable content, integrity failure, D1 outage, R2 outage with a warm cache.                           |

Each harness prints one line on success and stable failure codes on failure.
The codes, defined in `scripts/graphics-acceptance/evidence.mjs`, are the
contract: add codes, never rename one. `acceptance deferred` means nothing was
proved and is never a pass. Output never contains secrets, capability tokens,
filenames, object keys, or full URLs, so failing output is safe to paste into
an issue. Find identities in the installation by route and timestamp instead.

Step 2 asserts the installation serves **no** Content Security Policy today:
`csp-directive-unexpected` fires if one appears. If a restrictive policy is
added, flip `checkContentSecurityPolicy` to `settled: 'restrictive'`.
`--require-cache-hit` makes "edge never reported a warm cache" a failure; use
it once the deployment is known to reach the Workers Cache API.

#### Fault injection

Takes real delivery down while a fault is armed. **Never run it while anything
is on air.** Each procedure: arm, break one thing, run the fault mode, restore.

```bash
pnpm test:delivery:graphics:deployed --arm ~/.sk-armed.json
# break something (table below)
pnpm test:delivery:graphics:deployed --fault <name> --scenario ~/.sk-armed.json
# restore
```

The armed file contains live capability tokens; keep it private. It holds the
identities you need, including `cold.contentDigest`. Arming creates two
representations: `warm` (read once, so the edge caches it) and `cold` (never
read). A failed fault run keeps the file and its Events, because the file's
`content` array may be the only copy of bytes you deleted.

| Fault                            | Break                                                                       | Expected                                                                                                          | Restore                                                                   |
| -------------------------------- | --------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| `content-unavailable`            | Delete `sha256/<cold.contentDigest>` from `stream-graphics-asset-canonical` | Cold: 503 + `Retry-After` on capability and editor routes. Warm still serves.                                     | Re-upload from `cold.content`, or repair through the reconciliation queue |
| `content-integrity-disagreement` | Overwrite that object with different bytes of a different length            | Both routes 503 + `Retry-After`, no body. 200 means bad bytes reached a caller.                                   | Same                                                                      |
| `d1-outage`                      | Remove the `DB` binding (or point it at a missing ID) and deploy            | Both representations 503 + `Retry-After`, including the capability-session bootstrap. 200 means auth was skipped. | Restore binding, redeploy                                                 |
| `r2-outage-authorized-cache`     | Remove the `GRAPHICS_ASSET_CANONICAL` binding and deploy                    | Warm capability read still returns exact bytes; everything else 503 + `Retry-After`.                              | Restore binding, redeploy                                                 |

Always break the **cold** object for the first two: a warm capability route
serves cached bytes through a storage fault by design. The cache fault only
means something deployed; locally it reports `delivery-cache-not-observable`.

#### Safari automation

Gate 6 drives Safari through `safaridriver`: run `sudo safaridriver --enable`
once and tick **Develop → Allow Remote Automation**. Without automation the
harness reports `acceptance deferred path=manual-check-required`, and a
`:deployed` run refuses to defer unless given `--allow-manual`. A manual check
records only the browser fact, so gate 6 stays outstanding until an automated
run passes.

Safari 26.5 decodes VP9 alpha but flattens the alpha channel. So the product
blocks it instead: the Screen Output session opens, forecasts the revision in
`unplayableRevisions`, and the revision answers 409
`vp9-alpha-chromium-required`. The pass line reports `browserFact=`:
`substituted` (current Safari), `refused` (older Safari), or
`transparency-rendered`, which would mean the block may no longer be needed.
Locally the boundary cannot be exercised (no validator binding), so the run
reports `boundary=not-exercised`.

### Worker secrets

Set these against the generated config after building:

```bash
pnpm exec wrangler secret put <NAME> --config .output/server/wrangler.json
```

Required: `NUXT_BETTER_AUTH_SECRET`, `NUXT_GRAPHICS_ADMIN_TOKEN`,
`NUXT_SCREEN_OUTPUT_CAPABILITY_SIGNING_KEY`, `NUXT_ABLY_API_KEY`,
`NUXT_MELEE_CREDENTIAL_ENCRYPTION_KEY`,
`NUXT_MELEE_CREDENTIAL_ENCRYPTION_KEY_VERSION`. `NUXT_ADMIN_BOOTSTRAP_TOKEN` is
set only briefly (see [First admin](#first-admin-account)). Never put any of
them in `wrangler.jsonc`, source control, or public runtime config.

- **`NUXT_BETTER_AUTH_SECRET`**: without it the installation is unusable.
  `/api/**` denies by default and every check goes through Better Auth, so
  sign-in and every authenticated route answer 503.
- **`NUXT_SCREEN_OUTPUT_CAPABILITY_SIGNING_KEY`**: changing it revokes every
  Screen Output asset capability. Rotate each Screen's asset access afterwards
  before using its output URL.
- **Melee key rotation**: put the old version and key in
  `NUXT_MELEE_CREDENTIAL_ENCRYPTION_PREVIOUS_KEYS`, deploy the new key and
  version, re-save each enabled Melee integration, and remove the old key only
  once nothing uses it.

### Allowed hostnames

`AUTH_ALLOWED_HOSTS` in `server/utils/authOptions.ts` lists the origins Better
Auth accepts for state-changing requests: the custom domain plus loopback on any
port. Any other host gets 403 at sign-in. `*.workers.dev` is deliberately absent
(#410), because admitting the whole subdomain trusts hosts nobody here controls.
To sign in on one, add that exact hostname and rebuild.

### First admin account

Accounts are created by admins and there is no self sign-up, so a new
installation bootstraps its first admin with a temporary secret. The same steps
recover from every admin losing their password (there is no email sender, so no
reset link exists):

```bash
pnpm exec wrangler secret put NUXT_ADMIN_BOOTSTRAP_TOKEN --config .output/server/wrangler.json

curl -X POST https://stream.keepr.digital/api/bootstrap/ensure-admin \
  -H "x-admin-bootstrap-token: <token>" \
  -H 'content-type: application/json' \
  -d '{"email":"you@example.com","password":"<strong password>","name":"Your Name"}'

pnpm exec wrangler secret delete NUXT_ADMIN_BOOTSTRAP_TOKEN --config .output/server/wrangler.json
```

The response is `{"outcome":"created"}` or `{"outcome":"updated"}` (an existing
email gets the new password and the admin role). Repeating the call is safe.
It neither lifts a ban nor renames. **Delete the secret afterwards**: nothing
records that bootstrap happened, so the route stays armed while the secret
exists. Unset, the route answers 503.

### Other accounts

Admins manage everyone else at **`/admin/users`**, which asks for the Graphics
Administrator token.

- **Create**: makes a password-less account and returns a single-use invite
  link valid for 24 hours. Send it yourself; it is not stored or shown again.
  Always set a name: Graphics Authoring Lease notices name holders by it.
- **Reset link**: same kind of link for a forgotten password. Using it ends the
  account's other sessions.
- **Revoke sessions**: ends every session; the password stays. Sessions slide
  over 7 days of inactivity, so this is the only way to end one early.
- **Ban**: refuses sign-in and ends all sessions. Unbanning restores the old
  password.
- **Set password**: for an operator locked out mid-show. Prefer a reset link.

Screen Outputs use capabilities, not sessions, so none of the above affects
them.

## Access model

- **`/api/**` denies by default** (`server/middleware/api-session.ts`; the
  list is `server/utils/apiBoundary.ts`). Exempt: `/api/time`,
  `/api/realtime/token` (Screen Outputs have no session), Better Auth's own
  routes, the capability-authorized `/api/screen-output/**`, the secret-armed
  bootstrap route, and `/api/admin/**`.
- **`/api/admin/**` requires `x-graphics-admin-token`**, checked per route by
  `requireGraphicsAdministrator`. `test/unit/server/utils/apiBoundary.test.ts`
  proves every admin route reaches that guard. The admin pages hold the token
  in memory only.
- **Authentication, not authorization.** Every signed-in user sees every Graphic
  Asset; the library is installation-wide. Identity records who started work
  (for example a Graphics Ingestion Operation's `initiatedBy`), and an operation
  is 404 to anyone else.
- The SPA shell and static assets are public (`ssr: false`); client-side route
  guards are UX only. The API is the wall.

Realtime stays within the Ably **Free** plan by decision (#189). Validate
against its limits and report anything that would exceed them.

## Graphics Asset Library operations

Admin surfaces live under `/admin/graphics-assets`: the operations cockpit
(index), `health` (capacity limits), `queues`, and `evidence`. All `/api/admin/graphics-assets/**` routes need
`x-graphics-admin-token`.

### Scheduled work

`wrangler.jsonc` declares one hourly cron (`17 * * * *`). It runs retention
(`server/plugins/graphics-retention-schedule.ts`) and reconciliation
(`server/plugins/graphics-reconciliation-schedule.ts`) as independent handlers.
A failed pass is logged and swallowed; the next run resumes from durable state.
**A deploy without the cron silently stops automatic reclamation**; the backlog
then shows in the retention view.

NuxtHub (pinned `@nuxthub/core` 0.10.8) has no API for scheduled triggers,
object-store listing, Workflows, or Containers, so these use Cloudflare directly.
The exceptions are confined: all authoritative state stays in D1, all byte
access goes through the Graphics Object Store interface, and module tests run
without Cloudflare. Reassess when upgrading `@nuxthub/core`.

### Retention

The guarantees (`shared/utils/graphicsAssetRetention.ts`) are fixed. Storage
pressure never shortens them.

| State                            | Kept for                               |
| -------------------------------- | -------------------------------------- |
| Incomplete transfer              | 24 h after last progress               |
| Completed staged input           | 7 days                                 |
| Trashed Graphic Asset            | 30 days, restorable                    |
| Unreferenced superseded revision | 90 days                                |
| Unreachable content (quarantine) | 7 days, then rechecked before deletion |
| Evidence ledger entries          | 1 year                                 |

- `GET /api/admin/graphics-assets/retention` lists every deadline being held.
  `POST` runs a sweep now (safe any time; use it to drain a backlog).
- `GET …/evidence` is the audit trail. Successful sweeps log nothing else.
- `POST …/<assetId>/purge` with `{"confirmation":"purge-now"}` is the only way to
  reclaim Trash early.

Content deletion is two-phase (claim, delete bytes, recheck, drop the row), so
an outage never strands bytes without a catalogue record. A crashed claim
becomes reclaimable after a one-hour lease. Content that becomes reachable
mid-delete is marked Unavailable Graphic Asset Content with a
`content-deletion-conflict` entry: a repair case, not data loss.

**Unreleased staged input.** If the staging store is down when staged input
expires, the operation expires but its bytes stay counted against the staging
allowance. Every sweep retries the release indefinitely, and the **Unreleased
staged input** queue has a **Retry release** action. A warning alert stands
until the release lands, which records `staged-input-released`.

**Orphaned multipart uploads.** An in-flight multipart upload whose operation
row no longer exists is invisible to the sweep. Find and abort it with R2's S3
API:

```bash
aws s3api list-multipart-uploads --bucket stream-graphics-asset-staging \
  --endpoint-url https://<accountid>.r2.cloudflarestorage.com
aws s3api abort-multipart-upload --bucket stream-graphics-asset-staging \
  --key <key> --upload-id <UploadId> --endpoint-url https://<accountid>.r2.cloudflarestorage.com
```

### Reconciliation

Compares what the catalogue expects against what the canonical R2 bucket holds.
It never creates, redirects, or removes an asset, revision, or reference, so a
missed run only delays detection.

- **D1 is authoritative for what should be reachable; the byte store for which
  bytes exist.** `graphic_asset_contents.availability` is advisory:
  reconciliation is its only writer, and readers never trust it. A reader that
  sees the store answer and disagree reconciles that content immediately.
- **Each pass:** checks expectations least-recently-compared first; missing
  source bytes → Unavailable Graphic Asset Content (retryable, identities
  intact); missing derivative → regenerable discrepancy; size/type/digest
  mismatch → isolated **critical integrity incident**. It then scans one page of
  the store from a persisted cursor (a few thousand objects a day). Unexpected
  digest-owned keys go to 7-day quarantine and are never adopted. Non-digest
  keys become critical incidents and are never auto-deleted. Finally it reclaims
  stale repair/regeneration working copies.
- **Actions** (`/api/admin/graphics-assets/discrepancies/<id>`): `recheck`,
  `verify-stored-bytes` (full re-hash; the only way to detect same-size
  corruption, and the only action on an isolated incident),
  `regenerate-derivative` (must reproduce the recorded bytes exactly), and
  `PUT …/repair` with the exact original bytes (checked for length, SHA-256,
  validation, and recorded facts). There is no adopt action.
- **Isolated critical incidents are never repaired automatically.** Resolving a
  digest-key conflict is an operator decision.
- **Known limits:** deep verification only runs on an open discrepancy, so silent
  corruption behind agreeing metadata is detectable but not discovered. A
  verification immediately followed by a new incident on the same content is a
  race with retention deletion, not a new fault.

### Operations cockpit

`/admin/graphics-assets` reads `GET /api/admin/graphics-assets/operations-cockpit`:
one bounded, constant-cost snapshot composed from durable state. It reports the
catalogue and the canonical byte store as separate conditions (`degraded` or
`unavailable`) and still answers with `outcome: catalogue-unavailable` when D1 is
down.

- Severities: `critical` (cannot be trusted until someone acts), `warning` (a
  guarantee is at risk or an incident is retryable), `info`. Persistent alerts
  are backed by durable records and clear only when the incident does.
- Canonical quota boundaries: warning 80%, critical 95%, blocked 100%. The
  staging allowance is a separate budget.
- Actions: run reconciliation, run retention. Capacity limits are changed on
  `/admin/graphics-assets/health`; purge, repair, and verification stay on
  their own surfaces.

### Remote HTTPS copy

An author can copy a remote file into the library once, through the same
ingestion, validation, and publication path as an upload. Nothing keeps a link
to the remote host. The fetcher (`server/modules/graphics-asset-library/remote-source.ts`)
enforces at the first URL and at every redirect:

- public HTTPS only, no userinfo, only an `accept` header sent;
- at most three redirects, followed manually;
- every resolved A/AAAA record public (private, loopback, link-local, metadata,
  and embedded-IPv4 ranges rejected, Teredo rejected outright; `localhost`,
  `.local`, `.internal` refused before lookup);
- a transfer bounded by the kind's byte limit, at most one 16 MiB part resident.

Remote `Content-Type`, filename, and digest are ignored; the library derives
everything from the bytes. The URL is treated as a secret: it is never persisted,
logged, or stored in the browser, and errors show at most `scheme://host`. A
retry before any bytes are staged asks for the URL again. After server
validation the operation pauses at `awaiting-confirmation` for the browser to
decode the staged bytes and submit evidence.

DNS rebinding is mitigated, not prevented. Workers cannot pin `fetch` to a
resolved address or report the peer IP, so the resolver check (Cloudflare DoH)
is best-effort. Cloudflare's own subrequest restrictions are defence in depth.
A residual gap remains: a multipart upload is orphaned if the catalogue write
and the abort both fail in one attempt (see
[orphaned multipart uploads](#retention)).

### Silent-video validator

Silent-video publication requires server-side validation. Browsers only observe;
they cannot submit playback claims. The validator is a private Worker,
`stream-silent-video-validator` (`workers/silent-video-validator/`), reached
only through the `SILENT_VIDEO_PLAYBACK_VALIDATOR` service binding (no
`workers.dev` or preview URLs).

- Each validation idempotency key maps to one `silent-video-validation`
  Workflow instance. The Workflow re-verifies the staged object and streams it
  into a scale-to-zero Container. The Container is digest-pinned, uses Debian
  snapshot tooling, and has no network access. It proves complete decode, muted
  playback, seeks, and VP9-alpha transparency (ffprobe, ffmpeg, headless
  Chromium), and renders a deterministic transparent PNG poster fitted to
  640×360.
- Busy Containers answer 409 and the Workflow step retries. Durable state holds
  facts only, never bytes.
- Posters land under `validation/silent-video/` in the staging bucket. A
  30-day lifecycle rule, `silent-video-validation-posters`, created once with
  `wrangler r2 bucket lifecycle add`, reclaims them.
- An instance that ends errored or terminated is never restarted automatically.
  Fix the cause, then run
  `wrangler workflows instances restart silent-video-validation <id>`.
- Deploying needs Docker plus Workflows and Containers enabled on the account.
  Fixtures live in `scripts/silent-video-validator-fixtures.json`.
