# Stream Keepr

Event management and streaming overlay system for competitive gaming tournaments
(MTG, One Piece).

- **Event management**: tournament Events with game-specific settings.
- **Players and Matches**: player records, deck lists, pairings, results, best-of
  series, standings.
- **Streaming overlays**: card displays, deck views, match info, Feature Match
  Overlay, and Broadcast Graphics Screens rendered to OBS browser sources.
- **Melee integration**: sync tournament data from Melee.
- **Realtime**: live sync across connected clients via Ably.

This README is the single guide for developing, testing, deploying, and
operating Stream Keepr. The other docs:

| File           | Holds                                                                |
| -------------- | -------------------------------------------------------------------- |
| `CONTEXT.md`   | The domain glossary. Use its terms in code, tests, issues, and docs. |
| `DECISIONS.md` | Settled architecture decisions and why (cited as ADR-NNNN).          |
| `AGENTS.md`    | Rules for coding agents working in this repo.                        |
| `CHANGELOG.md` | Generated by release-please; never edit by hand.                     |

## Stack and layout

Nuxt 4 SPA (`ssr: false`), Vue 3, Pinia, Nuxt UI, Tailwind; Nitro on Cloudflare
Workers (`cloudflare_module` preset); D1 (SQLite) with Drizzle; R2 for graphics
bytes; Ably for realtime; Better Auth for accounts.

```text
app/        Frontend: pages, components, stores, composables
server/     Backend: API routes, modules, services, DB schema and migrations
shared/     Types and utilities shared by app and server
workers/    The silent-video validator Worker + Container
scripts/    Worker guards, acceptance harnesses, deploy helpers
build/      Nuxt build-time modules and local-configuration checks
test/       unit, nuxt, integration suites
```

## Setup

Use Node 24 LTS (24.11+; `.node-version` pins CI's exact version) and the pnpm
version pinned in `package.json`.

```bash
pnpm install
cp .env.example .env   # then fill in the values, see below
```

### Local configuration

`.env` at the repository root is the only local configuration file. It reaches
every way the app runs locally:

- `pnpm dev` and the test suites load it into `process.env`. A dev server
  missing required names warns once at boot rather than answering 503 per
  surface.
- `pnpm preview` copies it to `.output/server/.env`, because Wrangler resolves
  `.env` relative to its config file. Edit the root copy; the staged one is
  overwritten on every preview.
- Local acceptance harnesses read it directly and refuse to start if it lacks
  `NUXT_SCREEN_OUTPUT_CAPABILITY_SIGNING_KEY`, `NUXT_BETTER_AUTH_SECRET`, or
  `NUXT_ADMIN_BOOTSTRAP_TOKEN`.

`.env` is gitignored, so **a new git worktree starts without it**. Copy it in
when you create one (a worktree also needs its own `pnpm install`):

```bash
cp .env .claude/worktrees/<name>/
```

Without it, dev answers 503 from the admin and Screen Output surfaces, and the
two realtime integration tests skip. That is a configuration gap, not a
failure on `main`.

| Name                                             | Purpose                                                                                                                    |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| `NUXT_BETTER_AUTH_SECRET`                        | Signs sessions. Unset: sign-in and every authenticated route answer 503.                                                   |
| `NUXT_ADMIN_BOOTSTRAP_TOKEN`                     | Arms the first-admin route. Locally, leave it set; it is how a fresh checkout and the local harnesses get an account.      |
| `NUXT_GRAPHICS_ADMIN_TOKEN`                      | Graphics Administrator token for `/admin/**` pages and `/api/admin/**` routes.                                             |
| `NUXT_SCREEN_OUTPUT_CAPABILITY_SIGNING_KEY`      | 32-byte base64 HMAC key for Screen Output asset capabilities.                                                              |
| `NUXT_ABLY_API_KEY`                              | Ably key. Optional for tests: leave it empty rather than fake. A fake key makes one realtime test pass and the other fail. |
| `NUXT_MELEE_CREDENTIAL_ENCRYPTION_KEY`           | 32-byte base64 key encrypting Melee client secrets (AES-256-GCM).                                                          |
| `NUXT_MELEE_CREDENTIAL_ENCRYPTION_KEY_VERSION`   | Non-empty version label for the active key.                                                                                |
| `NUXT_MELEE_CREDENTIAL_ENCRYPTION_PREVIOUS_KEYS` | Optional JSON `{"<version>":"<key>"}` of retired keys still needed to decrypt during rotation.                             |

Generate keys and secrets with `openssl rand -base64 32`. A deployed Worker
reads no file; there these are Worker secrets (see [Worker secrets](#worker-secrets)).

## Development

| Launcher                | Serves                 | Auth                 |
| ----------------------- | ---------------------- | -------------------- |
| `pnpm dev`              | loopback               | Better Auth          |
| `pnpm dev:bypass`       | loopback               | Local Developer User |
| `pnpm dev:local`        | the LAN (`0.0.0.0`)    | Better Auth          |
| `pnpm dev:local:bypass` | the LAN (`0.0.0.0`)    | Local Developer User |
| `pnpm preview`          | loopback, built Worker | Better Auth          |
| `pnpm preview:bypass`   | loopback, built Worker | Local Developer User |

The `dev` launchers first apply pending migrations to the local D1 store Nitro
serves from (`.wrangler/state/v3`, bindings from `wrangler.dev.jsonc`).
`pnpm preview` builds, applies migrations to an ignored local D1 store under
`.wrangler/state/built-worker`, and runs the generated Worker under local
workerd. Neither touches a remote database.

Stop dev servers with Ctrl-C (SIGINT) or SIGTERM. A server killed with SIGKILL
or SIGHUP strands its `workerd` process, which then holds memory and sqlite
locks. `pnpm dev`, `pnpm preview`, their `:bypass` variants, `pnpm
worker:smoke`, and the integration suite reap orphans on start; `pnpm reap`
does it on demand. It only ever kills `workerd` whose parent is gone and whose
binary lives in a checkout Git lists for this repository (`git worktree list`):
the main checkout, worktrees nested under it, and worktrees anywhere else. A
reap from any one checkout covers them all; other repositories are untouched.

The same reap removes a leaked acceptance Chrome (#687): a headless Chrome
whose parent is gone and whose `--user-data-dir` is a
`stream-keepr-acceptance-<checkout>-*` profile named after one of those
checkouts, with its helper processes. Your own browsers never run under such a
profile, so they are never touched. The browser gates also stop their own
Chrome however they end, including a timeout and SIGINT/SIGTERM of the runner,
escalating to SIGKILL; the reap is for a runner that was itself SIGKILLed.

### Local auth bypass

The `:bypass` launchers set `STREAM_KEEPR_LOCAL_AUTH_BYPASS=true` on their own
command line. **That is the only place the name is written.** Never put it in
`.env`, `.env.example`, `wrangler.jsonc`, CI, or a Worker var. Nothing needs it:
builds, tests, `pnpm verify`, and CI behave identically without it. The server
compares it to the exact string `true` and infers nothing from `NODE_ENV`,
hostnames, or bindings. `pnpm worker:dry-run` fails if generated deploy config
carries it. `pnpm preview:bypass` stages it into `.output/server/.env`, which
every `nuxt build` wipes, so a deploy cannot pick it up.

Under a bypass:

- `NUXT_BETTER_AUTH_SECRET` and `NUXT_ADMIN_BOOTSTRAP_TOKEN` may be blank.
- Protected pages open as the stable **Local Developer User**. Each browser still
  gets its own Session, so Graphics Authoring Leases tell concurrent editors
  apart. The shell shows that identity and has no sign-out.
- Startup warns that authentication is bypassed.
- It does **not** cover the Graphics Administrator token, Screen Output
  capabilities, or any other configuration.

**`pnpm dev:local:bypass` gives every machine that can reach yours
unauthenticated access.** It exists for testing from a phone, tablet, or the
broadcast machine, where sign-in cannot work because a LAN address is not in
`AUTH_ALLOWED_HOSTS`. Use it only on a trusted network and stop it when done.
Binding any other bypassed launcher off loopback carries the same exposure
(ADR-0017, ADR-0018).

Before push, `pnpm verify:quick` is enough: CI is the full gate (below), and
running `pnpm verify` first would only repeat it. Open the PR as a draft and
mark it ready when the branch is done. Realtime integration tests are the one
gate CI cannot run, so a change touching realtime runs
`pnpm test:integration --run` locally first.

`pnpm verify` reproduces CI on the working tree. Its tail matters most:
`worker:dry-run` checks the upload bundle statically; `worker:smoke` runs it
under local workerd with production-shaped requests. Together they catch
bundles that pass on Node and break on workerd (#302), so reach for it when
CI's Worker job fails on a change to dependencies, bundling, `nuxt.config.ts`,
or server code.

How `pnpm verify` runs:

- **Cheap gates first.** `nuxt prepare`, then lint, typecheck, and the unit and
  Nuxt suites; the build runs beside them, and the silent-video validator's
  typecheck and bundle check start at once beside `nuxt prepare`. The
  server-backed suites and browser
  gates start only once those pass, so a lint or type error arrives in seconds.
- **Each gate logs to `node_modules/.cache/verify/<gate>.log`.** The terminal
  shows one line per gate and the tail of the first failure.
- **Lint and typecheck are cached** (`node_modules/.cache/eslint/`,
  `node_modules/.cache/tsc/`), so an unchanged tree lints and typechecks in
  seconds. The ESLint cache is per file, so a type-aware rule can miss a finding
  in an unchanged file that a changed file's types caused; CI starts cold and
  catches it. Delete the cache directory to reproduce CI exactly.
- **Only `nuxt prepare` writes `.nuxt`.** The root tsconfig extends it, so every
  other gate reads it (except the validator's two, whose tsconfig stands alone); the Nuxt suite, the servers and `verify`'s build each use
  their own build directory. Keep it that way when adding a gate. Dev servers
  started together also need their own Vite cache (`nuxt.config.ts` gives each
  one), or they rewrite each other's optimised dependencies.
- **Tried and rejected** (measured on a 10-core machine, September 2026):
  integration test files in parallel against one server (they assert
  library-wide state); `--no-isolate` for the Nuxt suite (about 4× faster, but
  83 files fail on leaked state); Vitest's `fsModuleCache` (no gain on the
  unit suite, breaks the Nuxt suite on a warm cache; on by default since
  Vitest 5, so `vitest.nuxt.config.ts` turns it off); `pool: 'threads'`
  (no gain); ESLint `--concurrency` and `projectService` (slower, and
  `projectService` exhausts the heap).

CI (`.github/workflows/ci.yml`) runs the same gates as `pnpm verify` on PRs
and in the merge queue, split across parallel jobs (checks, two integration
shards, local-auth and browser gates, Worker build) so the longest job sets the
wall time. The queue's run tests the exact tree that lands
([Releases](#releases)). It skips draft PRs (marking one ready runs it),
changes that touch only docs, and the Worker build when only tests, docs or
the other workflows changed (`scripts/ci-scope.mjs` decides, against a PR's
base or the queue's base, and runs everything when it cannot tell). A merge
group also skips the gates when its tree is byte-identical to one a full, green
PR run verified: one PR, with `main` unchanged since its PR run. That PR run's
`record` job leaves a GitHub-signed OIDC token naming the commit it ran on, and
`scripts/ci-reuse.mjs` checks it (ADR-0036). The scope job's log and `CI passed`
then name the run that verified the tree. Any doubt runs everything. A newer
push cancels the older PR run. It is the full gate: before it,
`pnpm verify:quick`.
Realtime integration tests self-skip in CI: no Ably key is configured there, by
decision (#189). The suites in the table above that need a running preview,
Docker, or a real store stay local. Other vitest modes work directly,
e.g. `pnpm exec vitest --ui`.

Gotchas:

- **Run integration suites one at a time.** Concurrent runs, or a loaded
  machine, make every result meaningless. A cascade of `ECONNREFUSED` or
  "session cookie was not issued" with zero assertion failures means a
  `workerd` backend died, not that the code broke.
- **The integration suite runs several servers.** One `nuxt dev` per vitest
  worker, each over its own database under `.wrangler/state/integration-<n>`, so
  test files run in parallel but never two against one database. The default is
  a third of the CPU cores, at most four; set `STREAM_KEEPR_INTEGRATION_SERVERS`
  to change it (`1` is the old serial run). Each server's output is kept in
  `node_modules/.cache/integration-servers/`. The servers share one Ably app,
  and channels are named by Event id, so each server mints Event ids from its
  own block of a million (`integrationEventIdBlocks`); without that, two files
  hear each other's publications (#630).
- **A failed integration test prints its requests.** The
  `[integration] requests during "…"` block lists each request with its time;
  on a timeout, the one marked `never returned` is the stall. It names the
  route, not the step inside it, and a `beforeAll` stall prints nothing. The
  `[integration] server log during "…"` block beneath it is what that test's
  server logged meanwhile (the last 40 lines): a refusal's
  `api_request_failed` line, and for a Graphics Asset 503 the
  `graphics_object_store_unavailable` or `graphics_catalogue_unavailable` line
  saying what R2 or D1 threw. The full log is
  `node_modules/.cache/integration-servers/<server>.log`, overwritten by the
  next run.
- **An early answer's body is read to its end** (#633). When a route answers
  without reading its request body (a multipart part already held, a body over
  its limit), Nitro's dev proxy stops forwarding the rest, and the public
  listener keeps the connection alive with those bytes unread. A client that
  reuses it waits behind them until the keep-alive timeout (5 s plus Node's 1 s
  buffer) resets it, 6 s after the early answer, with nothing logged: CI's
  `complete` after a duplicate part died that way. The integration servers read
  and discard such a body (`test/integration/earlyAnswerDrain.mjs`), as Node
  does for one nobody started reading; a deployed Worker is not served by
  `nuxt dev`.
- **A dropped connection leaves an `[integration-server]` line** (#633). Each
  server runs with `test/integration/serverConnectionDiagnostics.mjs`
  preloaded, in `nuxt dev`'s main thread (the public listener and Nitro's
  proxy) and in Nitro's dev worker thread. It writes one line when a request's
  connection closes before its response finished, a proxy hop fails or is cut
  off, a socket times out with a request in flight, the public listener's
  keep-alive timeout closes a connection, a worker thread starts or exits (a
  dev worker reload), or a thread's event loop stalls for a second or more. A
  line carries the method, the path without its query, timings and Node's error
  code; never a header or a body. The failure report also says when the test
  worker's own event loop stalled.
- **Nuxt-suite failures under load are often timing.** A 30s `setupNuxt`
  timeout shows skipped tests; 5s per-test timeouts show bimodal durations.
  Re-run the single file, then the suite with `--no-file-parallelism`, before
  believing a broad failure.
- **The Nuxt suite is selected by config**, not project:
  `vitest --config vitest.nuxt.config.ts`.
- **Local acceptance harnesses target `http://127.0.0.1:8787`**, whichever
  checkout is serving it, and provision real Events there. Set
  `STREAM_KEEPR_LOCAL_ACCEPTANCE_URL` to aim at your own preview.
- **Use `pnpm lint`**, not `npx eslint`, which resolves nothing locally and exits 0. ESLint also exits 0 on warnings, so read the output.

## Database

```bash
pnpm db:generate  # drizzle-kit: generate a migration from schema changes
pnpm db:migrate   # apply migrations to the local dev D1 (the dev launchers do this too)
```

`db:migrate` reads stdin from `/dev/null`, so Wrangler takes its
non-interactive "yes" instead of asking before applying to the local store.

The schema is `server/db/schema.ts` plus `server/db/schema/*.ts`
(`drizzle.config.ts`); migrations live in `server/db/migrations/sqlite`. Server
code queries through `db` from `~~/server/db`. Wrangler records applied
migrations in `_hub_migrations`; production's history is in that table, so the
name must not change.

The history starts at `0000_baseline.sql`, squashed before first ship while no
database held data (ADR-0019). Its tail is hand-written — a seed row and the
Screen Deck-source triggers — because drizzle-kit cannot generate either;
`test/unit/server/db/baselineMigration.sqlite.test.ts` fails if a re-squash
drops them.

The squash was a one-time transition. A D1 whose `_hub_migrations` still lists
the old `0000`–`0031` names reads `0000_baseline` as unapplied and fails on its
existing tables, so such a database is dropped and recreated once (ADR-0019
required this of production before the squash deployed). A D1 that has applied
`0000_baseline` is past the transition: it takes later migrations as they come
and is never wiped for this.

**Read every generated migration before committing it.** SQLite refuses
`ALTER TABLE … ADD COLUMN … NOT NULL` without a `DEFAULT`, but only when the
table has rows, so a missing default passes locally and fails on the first
replay against real data (#310). `pnpm db:generate` will not add one; you do.
If the new column has a unique index, a constant default collides, so backfill
per row between the `ALTER` and the `CREATE UNIQUE INDEX` (`hex(randomblob(n))`
or the row's primary key). A migration that alters or rewrites populated tables
gets a test that holds it back with `createSqliteD1Harness({ throughMigration })`,
inserts rows, then runs `applyRemainingMigrations()`.

D1 records applied migrations **by name**, so editing a migration changes
nothing wherever it already ran; only a database that has not applied it sees
the edit. Repair a migration in place only while it is known to be unapplied
everywhere that matters: still on your branch, or unreleased and run only on
local stores you will reset. Once a deployed installation has applied it,
correct it forward with a new migration. An in-place edit would leave that
installation on the old SQL while fresh replays get the new, and nothing would
report the difference.

## Releases

release-please (`.github/workflows/release-please.yml`) versions from
conventional commits: `fix:` → patch, `feat:` → minor, `feat!:` or
`BREAKING CHANGE` → major. It keeps one rolling Release PR against `main`.
**Merging that PR (through the merge queue) is the release**: it tags
`vX.Y.Z`, publishes a GitHub Release, bumps `package.json`, and updates
`CHANGELOG.md`. `main` is trunk; there is no `develop` branch.

How a change reaches `main`, and why:

- **Every change lands through the merge queue, as a squash commit.** The
  repository allows only squash merges, with the PR title as the commit title,
  so each PR is one conventional commit and one changelog line. Merge commits
  bring every branch commit along, and a branch merged both locally and by its
  PR listed each change twice (Release PR #400). Never push or merge to `main`
  directly: that skips the queue's CI.
- **The queue verifies the exact revision that lands** (ADR-0036). "Merge when
  ready" adds a PR whose required checks passed to the queue, which squashes
  it onto `main` plus every PR queued ahead of it, and runs CI and the title
  check on that combined commit (`merge_group`). Only if they pass does `main`
  fast-forward to that very commit, so two PRs that each passed against an old
  `main` cannot land an untested combination. Each entry must pass on its own
  (grouping `ALLGREEN`), so every commit `main` holds passed. A PR that fails
  is removed from the queue, and the ones behind it are re-tested without it.
  PR runs are
  feedback and the entry ticket; the queue's run is the one that counts. When
  the group's tree is exactly the one a full, green PR run already verified,
  the queue's run reuses that verification and skips the gates rather than
  repeating ten minutes of CI on identical bytes (see [Testing](#testing)).
- **PR titles are Conventional Commits**, checked by
  `.github/workflows/pr-title.yml`. A title that is not one would drop the PR
  from the changelog and the version bump. In the queue it checks the subject
  of every squash commit the group would land, which is what release-please
  reads.
- **The `main` ruleset enforces it**: a PR is required, merges go through the
  merge queue, squash is the only merge method, history stays linear,
  force-pushes and deletion are refused, and `CI passed` plus
  `Conventional Commit title` must be green on the PR and on its merge group.
  It has no bypass actor, so nothing reaches `main` around the queue; Release
  PRs, which once needed an admin bypass, now go through it too. The **release
  tags** ruleset makes `v*` tags immutable, and repository admins can bypass
  it. `CI passed` is one summary job that always reports, so CI can skip what
  a change cannot affect without leaving a required check waiting. The
  `production` and `production-validator` promotion-marker tags
  ([Promotion markers](#promotion-markers)) are unprotected: every deploy
  force-moves them, and GitHub refuses the Actions app as a ruleset bypass
  actor.
- **A release is cut only from a revision the queue verified.** release-please
  tags the Release PR's merge commit, which through the queue is the commit CI
  passed on. Before it runs, `scripts/release-gate.mjs` checks every merged
  Release PR still awaiting its tag (`autorelease: pending`) and fails the
  workflow, tagging nothing, if no successful `merge_group` CI run is recorded
  for that commit, waiting up to two minutes for one still finishing. A run
  that reused a PR run's verification counts: the guarantee is that the
  commit's tree passed a full, green CI run, which is the case when it is
  byte-identical to the tree that run verified. Only a
  Release PR merged around the queue (a bypass, or a merge while the queue was
  off) can trip it; re-run the workflow once in case the queue's run was slow.
  It stops every release-please run until resolved by hand: verify that
  commit yourself, create its release
  (`gh release create vX.Y.Z --target <commit>` with the changelog section),
  and relabel the PR from `autorelease: pending` to `autorelease: tagged`.
- **Release PRs need their CI approved.** release-please opens and updates the
  Release PR with the default workflow token, and GitHub creates the
  `pull_request` runs such a token triggers as **approval-required**
  (`action_required`) rather than starting them, so a workflow cannot trigger
  itself. To release, wait until the queue is empty and release-please has
  refreshed the Release PR from the last push, select **Approve workflows to
  run**, wait for the checks, then **Merge when ready**, and queue nothing else
  until it lands. Queued behind another PR, the release would tag that PR's
  change without its changelog line; and a push to `main` while it waits
  rewrites the Release PR, which drops it from the queue and needs a fresh
  approval. Run the workflow by hand (`gh workflow run release-please.yml`) to
  refresh the Release PR without a push. A GitHub App token for release-please
  would start its runs without the approval.

Requires Settings → Actions → General → **Allow GitHub Actions to create and
approve pull requests**. The default workflow token is read-only; each workflow
declares the scopes it needs.

## Deploy

Nitro generates the deployable config at `.output/server/wrangler.json` from
`wrangler.jsonc`, which declares every binding (D1, KV, R2, service) with its
production ID, plus routes, cron and observability. Deploys use the
repo-pinned Wrangler.

There is no separate staging environment: **production is the staging gate.**
The production hostname is `https://stream.keepr.digital`, attached as a
`custom_domain` route in `wrangler.jsonc`.

`pnpm run deploy` runs, in order and stopping at the first failure:

1. `pnpm build`.
2. `pnpm worker:dry-run`: bundles what Wrangler would upload into
   `.output/wrangler-dry-run/` and fails if it contains
   `new WebAssembly.Module(`, which a deployed Worker refuses (every JPEG/WebP
   ingestion would fail, #302). It also fails if the bypass name appears in
   generated config.
3. `pnpm worker:smoke` against that production build.
4. `pnpm deploy:mark-app pending`: moves the `production` marker to this
   checkout as `pending` before anything remote changes
   ([Promotion markers](#promotion-markers)). If it cannot, nothing deploys.
5. `pnpm db:migrate:remote`.
6. `wrangler deploy`.
7. `pnpm deploy:verify` (`scripts/deploy-verify.mjs`): reads `GET /api/time`
   and passes only on status 200, `application/json`, and a
   `{ serverTime: <epoch ms> }` body. A redirect fails and is never followed,
   so an Access or login page cannot pass, and neither can an HTML fallback.
   Only unreachable, 5xx and 429 answers are retried. Set
   `STREAM_KEEPR_DEPLOY_HEALTH_URL` only to verify a different origin.

   It proves **liveness only**: some Worker on that origin answers with this
   app's handler. `/api/time` carries no build identity, so the previous
   release passes too, and it reads no binding, so it says nothing about D1,
   auth, R2, KV, Ably or the validator. The deployed gates (Deploy day, step 5)
   cover those. `worker:smoke` runs the same probe against the built Worker.

8. `pnpm deploy:mark-app deployed`: marks the app deployed, only once
   `deploy:verify` has passed.

Migration and promotion are separate Cloudflare operations, not one
transaction. Schedule incompatible schema changes for a maintenance window.

`pnpm deploy:validator` deploys the validator the same way: it marks
`production-validator` `pending` with this checkout's fingerprint, runs
`wrangler deploy` on `workers/silent-video-validator/wrangler.jsonc`, and then
marks it `deployed`.

### Promotion markers

The app and the validator are deployed separately and can fail separately.
Each has its own marker, an annotated git tag on `origin` (ADR-0035):

| Tag                    | Component | Moved by                                                  |
| ---------------------- | --------- | --------------------------------------------------------- |
| `production`           | App       | `pnpm run deploy` (steps 4 and 8), or the Deploy workflow |
| `production-validator` | Validator | `pnpm deploy:validator`, or the Deploy workflow           |

A marker records the component, its state, the commit it was deployed from,
whether that checkout had uncommitted or untracked changes (`worktree: dirty`),
who deployed it (a workflow run or `local`), and for the validator its
**fingerprint**. Every deploy marks its component `pending` before it changes
anything, and `deployed` once it succeeded. A deploy that died part-way leaves
`pending`, which means "unconfirmed: either version may be serving". A deploy
that cannot write its pending marker does not start. `pnpm deploy:status`
prints both markers and says whether this checkout's validator would deploy.
It reads `origin` and bundles the validator (`pnpm validator:dry-run`), so it
needs network access and installed dependencies, but no Docker or Cloudflare
credentials.

Markers are force-pushed, and the last writer wins. Deploy runs are serialised,
but nothing stops a local deploy during one, so don't start one. A local deploy
from unpushed commits pushes them to `origin` along with its marker tag.

The validator fingerprint is a sha256 of what `wrangler deploy` would upload
and build: the bundle `pnpm validator:dry-run` produces (every import it
resolves, so a root dependency such as `@cloudflare/containers` or a
`shared/` module counts), every file in the Container's Docker context
(`container/`), and its `wrangler.jsonc`. A release's version bump changes none
of them, so it does not redeploy the validator.

Deploying the validator with bare `wrangler deploy`, or rolling it back from the
dashboard or with `wrangler rollback`, bypasses its marker. If that happened,
run the next Deploy with `validator: always`, or `pnpm deploy:validator` from
the checkout you want.

### Deploy from GitHub Actions

The **Deploy** workflow (`.github/workflows/deploy.yml`) is manual-only and runs
what `pnpm run deploy` runs, but ships a **released tag**, never `main`'s HEAD:

- `version`: `latest` (default) or a tag like `v1.2.0`. Rollback is dispatching
  it with the previous tag.
- `d1_recovery_point`: must be typed `confirmed`.
- `validator`: `auto` (default) deploys the validator first unless
  `production-validator` records a confirmed deploy with the release's
  fingerprint. A missing, unreadable or `pending` marker, or a release that
  cannot be bundled, deploys it. `always` and `never` override; `never` leaves
  the marker alone.

The run is one step, `scripts/deploy-promotion.mjs promote`: validator first
when decided, then `pnpm run deploy`, each between its markers. It runs that
script from the workflow's own commit, not from the release, so rolling back
to a release from before the markers still keeps them. The step summary
records the validator decision, and on failure what each marker now says.

It needs the `CLOUDFLARE_API_TOKEN` (Workers Scripts:Edit, D1:Edit, plus
Containers when deploying the validator) and `CLOUDFLARE_ACCOUNT_ID` secrets on
the `production` environment, which deploys only from `main`: a workflow on any
other branch cannot read them. The acceptance gates and the "nothing on air" check stay with the
operator.

### Deploy day

Run these in order from a working checkout. Every gate provisions real Events
and assets in production and deletes them afterwards. A harness that dies
mid-run names the Event it left behind; delete it before rerunning.

1. **Pre-flight.** Nothing on air. Docker running. Secrets present
   (`pnpm exec wrangler secret list --name stream`). No leftover `workerd`
   (`pnpm reap`).
2. **Recovery point.** Build the production config, inspect pending
   migrations, and confirm a recent D1 Time Travel recovery point or export
   exists:

   ```bash
   pnpm build
   pnpm db:migrations:list:remote
   ```

3. **Deploy.** Deploy the validator first when `pnpm deploy:status` says it
   would deploy (it always does on a first deploy), so the service binding
   resolves:

   ```bash
   pnpm deploy:status      # both markers; whether this validator would deploy
   pnpm deploy:validator   # when it would
   pnpm run deploy
   ```

   If `deploy:verify` fails, stop and roll back: redeploy the previous Worker
   version (dashboard → Workers & Pages → Deployments, or
   `wrangler rollback`), then restore any applied migration from the recovery
   point. The `production` marker stays `pending` until the next deploy
   confirms one, which is accurate: the rollback is not recorded. Then
   follow [Recovering from a partial promotion](#recovering-from-a-partial-promotion).

#### Recovering from a partial promotion

A deploy that fails after the validator succeeded leaves the components on
different releases. Read the markers first (`pnpm deploy:status`, or the failed
run's step summary). For example, with A in production, a Deploy of B that
fails in `pnpm run deploy` leaves:

- `production-validator`: `deployed` B: B's validator is serving.
- `production`: `pending` B, so A or B may be serving. A Deploy run marks it
  pending before `pnpm run deploy` starts, so this holds whether the failure
  came in the build or at the verify. A local `pnpm run deploy` that fails in
  its build, dry run or smoke test leaves it `deployed` A, because that run
  marks pending only right before the D1 migration.

Pick the release production should run, then deploy it whole:

- **Back to A**: dispatch Deploy with `version` A. Its fingerprint differs from
  B's, so `auto` redeploys A's validator before A's app. As in step 3, restore
  any migration B applied from the recovery point. Releases whose validators are
  identical have identical fingerprints, so no validator redeploy happens
  there, and none is needed.
- **Forward to B**, once fixed: dispatch B again. Its validator is already
  confirmed, so only the app deploys.
- **Locally**, when Actions is not an option: check out that release, then
  `pnpm deploy:validator` (when `pnpm deploy:status` says it would deploy) and
  `pnpm run deploy`. Both record their markers, `worktree: dirty` included.

A `pending` validator marker means its deploy died part-way, so the next
`auto` run always redeploys it, even at the same fingerprint.

4. **Set the harness variables:**

   | Variable                                    | Value                                                                             |
   | ------------------------------------------- | --------------------------------------------------------------------------------- |
   | `STREAM_KEEPR_BROWSER_ACCEPTANCE_URL`       | The installation to test. Falls back to `STREAM_KEEPR_DEPLOY_HEALTH_URL`.         |
   | `STREAM_KEEPR_ACCEPTANCE_OPERATOR_EMAIL`    | An existing operator account. `/api/**` denies by default, so gates must sign in. |
   | `STREAM_KEEPR_ACCEPTANCE_OPERATOR_PASSWORD` | That account's password.                                                          |
   | `CLOUDFLARE_ACCOUNT_ID`                     | The installation's account. The validator gate writes with Wrangler on it alone.  |

   A `--deployed` harness refuses to start without a URL rather than guessing.
   Without the operator pair it stops with `harness-operator-unavailable`.
   Setting `NUXT_ADMIN_BOOTSTRAP_TOKEN` in the shell also works if that secret is
   armed on the installation for the run.

   The URL must be a host the committed `wrangler.jsonc` serves. The validator
   gate stages in the bucket and triggers the Workflow that the committed app
   and validator configs bind, so any other URL stops with
   `harness-target-inconsistent reason=origin-not-installation` before anything
   is written (`scripts/graphics-acceptance/deployed-target.mjs`, #619).

5. **Run the gates.** `pnpm accept deployed` runs steps 1–6 in order and
   stops at the first failure; run one alone with `pnpm accept <name> --deployed`.
   It checks the whole target first (URL, operator, account, config agreement)
   and runs no gate if any of it is missing, so the first gate cannot write
   before a later one refuses.

   | #   | Harness                             | Proves                                                                                                    |
   | --- | ----------------------------------- | --------------------------------------------------------------------------------------------------------- |
   | 1   | `silent-video-validator`            | The validator Workflow and Container accept H.264 MP4, VP9 WebM, and VP9-alpha WebM with correct posters. |
   | 2   | `graphics-delivery`                 | Full and ranged delivery, ETags, caching, authorization, revocation, CORS/CSP, failure outcomes.          |
   | 3   | `still-images`                      | PNG, JPEG, and WebP decode in an OBS-like output.                                                         |
   | 4   | `silent-video`                      | MP4 and WebM play and seek; VP9 alpha keeps transparency on Chromium.                                     |
   | 5   | `fonts`                             | A library font revision is delivered, loads, and renders its glyphs.                                      |
   | 6   | `graphics-package`                  | Template Package publication is atomic and its retry is idempotent.                                       |
   | 7   | [Fault injection](#fault-injection) | Unavailable content, integrity failure, D1 outage, R2 outage with a warm cache.                           |

**Validator gate cleanup.** The validator gate stages fixtures directly, with
no Graphics Ingestion Operation that retention could find, so it records every
key in `.cache/acceptance/silent-video-validator-cleanup.json` (private,
gitignored) before writing it, and deletes them all at the end. A delete that
fails leaves the file, fails the run with `harness-cleanup-incomplete`, and
makes the next run stop with `harness-cleanup-pending`. A poster stays listed
until its Workflow instance is seen to settle, since the instance may still
write it. Retry with `pnpm accept silent-video-validator --deployed --cleanup`
with the same URL and account (no operator needed); it is safe to repeat. The
Workflow instances stay, holding facts only.

Each harness prints one line on success and stable failure codes on failure.
The codes, defined in `scripts/graphics-acceptance/evidence.mjs`, are the
contract: add codes, never rename one. Output never contains secrets,
capability tokens, filenames, object keys, or full URLs, so failing output is
safe to paste into an issue. Find identities in the installation by route and
timestamp instead.

Step 2 asserts the installation serves **no** Content Security Policy today:
`csp-directive-unexpected` fires if one appears. If a restrictive policy is
added, flip `checkContentSecurityPolicy` to `settled: 'restrictive'`.
`--require-cache-hit` makes "edge never reported a warm cache" a failure; use
it once the deployment is known to reach the Workers Cache API.

#### Fault injection

Takes real delivery down while a fault is armed. **Never run it while anything
is on air.** Each procedure: arm, break one thing, run the fault mode, restore.

```bash
pnpm accept graphics-delivery --deployed --arm ~/.sk-armed.json
# break something (table below)
pnpm accept graphics-delivery --deployed --fault <name> --scenario ~/.sk-armed.json
# restore
```

The armed file contains live capability tokens; keep it private. It holds the
identities you need, including `cold.contentDigest`. Arming creates two
representations: `warm` (read once, so the edge caches it) and `cold` (never
read). A failed fault run keeps the file and its Events, because the file's
`content` array may be the only copy of bytes you deleted.

| Fault                            | Break                                                                       | Expected                                                                                                          | Restore                                                                   |
| -------------------------------- | --------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| `content-unavailable`            | Delete `sha256/<cold.contentDigest>` from `stream-graphics-asset-canonical` | Cold: 503 + `Retry-After` on capability and editor routes. Warm still serves.                                     | Re-upload from `cold.content`, or repair through the reconciliation queue |
| `content-integrity-disagreement` | Overwrite that object with different bytes of a different length            | Both routes 503 + `Retry-After`, no body. 200 means bad bytes reached a caller.                                   | Same                                                                      |
| `d1-outage`                      | Remove the `DB` binding (or point it at a missing ID) and deploy            | Both representations 503 + `Retry-After`, including the capability-session bootstrap. 200 means auth was skipped. | Restore binding, redeploy                                                 |
| `r2-outage-authorized-cache`     | Remove the `GRAPHICS_ASSET_CANONICAL` binding and deploy                    | Warm capability read still returns exact bytes; everything else 503 + `Retry-After`.                              | Restore binding, redeploy                                                 |

Always break the **cold** object for the first two: a warm capability route
serves cached bytes through a storage fault by design. The cache fault only
means something deployed; locally it reports `delivery-cache-not-observable`.

#### Transparent video is Chromium-only

Screen Outputs and authoring are supported on Chromium only (ADR-0020). A
VP9-alpha revision is delivered to every engine alike; a browser that cannot
keep its alpha flattens it, and nothing detects or refuses that browser. Gates 1

### Worker secrets

Set these against the generated config after building:

```bash
pnpm exec wrangler secret put <NAME> --config .output/server/wrangler.json
```

Required: `NUXT_BETTER_AUTH_SECRET`, `NUXT_GRAPHICS_ADMIN_TOKEN`,

- **`NUXT_SCREEN_OUTPUT_CAPABILITY_SIGNING_KEY`**: changing it revokes every

- **Melee key rotation**: put the old version and key in

### Allowed hostnames

`AUTH_ALLOWED_HOSTS` in `server/utils/authOptions.ts` lists the origins Better
Auth accepts for state-changing requests: the custom domain plus loopback on any
port. Any other host gets 403 at sign-in. `*.workers.dev` is deliberately absent
(#410), because admitting the whole subdomain trusts hosts nobody here controls.
To sign in on one, add that exact hostname and rebuild.

### Session cookies

Every built server, meaning a deployment, `pnpm preview` and `pnpm
worker:smoke`, sets the Session as `__Secure-better-auth.session_token` with
`Secure; HttpOnly; SameSite=Lax; Path=/`. Only `nuxt dev` (the `dev` launchers
and the integration and local-auth suites) sets it unprefixed and without
`Secure`, as it always has. The split is `advanced.useSecureCookies` in
`server/utils/authOptions.ts`, decided by the build rather than by `NODE_ENV`
(ADR-0012, #451). Chromium keeps a `Secure` cookie on loopback, so signing in
to `pnpm preview` works there; a browser that does not treat
`http://127.0.0.1` as secure (WebKit, historically) will not keep it. `pnpm
worker:smoke` fails if the built Worker's cookie lacks any of those
attributes. Observing the deployed origin's cookie is still open on #451.

The first deploy with this split ends every browser's sign-in once. An older
unprefixed cookie is ignored rather than refused, so the person simply signs
in again, and its D1 Session lapses after 7 days.

### Sign-in rate limit

Every built server limits Better Auth's routes per client, keyed on
`cf-connecting-ip` and counted in D1's `rateLimit` table: three sign-in
attempts per 10 seconds, then 429 with `X-Retry-After`. `nuxt dev` does not
limit. The policy is `rateLimit` in `server/utils/authOptions.ts`
(ADR-0012, #697), and `pnpm worker:smoke` fails if the built Worker admits a
fourth attempt. Under `pnpm preview` every local caller is one client, so a fourth
sign-in within 10 seconds is refused there too.

### First admin account

Accounts are created by admins and there is no self sign-up, so a new
installation bootstraps its first admin with a temporary secret. The same steps
recover from every admin losing their password (there is no email sender, so no
reset link exists):

```bash
pnpm exec wrangler secret put NUXT_ADMIN_BOOTSTRAP_TOKEN --config .output/server/wrangler.json

curl -X POST https://stream.keepr.digital/api/bootstrap/ensure-admin \
  -H "x-admin-bootstrap-token: <token>" \
  -H 'content-type: application/json' \
  -d '{"email":"you@example.com","password":"<strong password>","name":"Your Name"}'

pnpm exec wrangler secret delete NUXT_ADMIN_BOOTSTRAP_TOKEN --config .output/server/wrangler.json
```

The response is `{"outcome":"created"}` or `{"outcome":"updated"}` (an existing
email gets the new password and the admin role). Repeating the call is safe.
It neither lifts a ban nor renames. **Delete the secret afterwards**: nothing
records that bootstrap happened, so the route stays armed while the secret
exists. Unset, the route answers 503.

### Other accounts

Admins manage everyone else at **`/admin/users`**, which asks for the Graphics
Administrator token.

- **Create**: makes a password-less account and returns a single-use invite
  link valid for 24 hours. Send it yourself; it is not stored or shown again.
  Always set a name: Graphics Authoring Lease notices name holders by it.
- **Reset link**: same kind of link for a forgotten password. Using it ends
  every session the account holds and signs nobody in.
- **Revoke sessions**: ends every session; the password stays. Sessions slide
  over 7 days of inactivity; this, a used reset link, and a ban are what end
  one early.
- **Ban**: refuses sign-in and ends all sessions. Unbanning restores the old
  password.
- **Set password**: for an operator locked out mid-show. Prefer a reset link.

Screen Outputs use capabilities, not sessions, so none of the above affects
them.

## Access model

- **`/api/**` denies by default** (`server/middleware/api-session.ts`; the
  list is `server/utils/apiBoundary.ts`). Exempt: `/api/time`,
  `/api/realtime/token` (Screen Outputs have no session), Better Auth's own
  routes, the capability-authorized `/api/screen-output/**`, the secret-armed
  bootstrap route, and `/api/admin/**`.
- **`/api/admin/**` requires `x-graphics-admin-token`**, checked per route by
  `requireGraphicsAdministrator`. `test/unit/server/utils/apiBoundary.test.ts`
  proves every admin route reaches that guard. The admin pages hold the token
  in memory only.
- **Authentication, not authorization.** Every signed-in user sees every Graphic
  Asset; the library is installation-wide. Identity records who started work
  (for example a Graphics Ingestion Operation's `initiatedBy`), and an operation
  is 404 to anyone else.
- The SPA shell and static assets are public (`ssr: false`); client-side route
  guards are UX only. The API is the wall.

Realtime stays within the Ably **Free** plan by decision (#189). Validate
against its limits and report anything that would exceed them.

## Graphics Asset Library operations

Admin surfaces live under `/admin/graphics-assets`: the operations cockpit
(index), `health` (capacity limits), `queues`, and `evidence`. All `/api/admin/graphics-assets/**` routes need
`x-graphics-admin-token`.

### Scheduled work

`wrangler.jsonc` declares one hourly cron (`17 * * * *`). It runs retention
(`server/plugins/graphics-retention-schedule.ts`) and reconciliation
(`server/plugins/graphics-reconciliation-schedule.ts`) as independent handlers.
A failed pass is logged and swallowed; the next run resumes from durable state.
**A deploy without the cron silently stops automatic reclamation**; the backlog
then shows in the retention view.

Scheduled triggers, object-store listing, Workflows, and Containers are
Cloudflare-specific. That provider knowledge stays confined: all authoritative
state stays in D1, all byte access goes through the Graphics Object Store
interface, and module tests run without Cloudflare.

### Retention

The guarantees (`shared/utils/graphicsAssetRetention.ts`) are fixed. Storage
pressure never shortens them.

| State                            | Kept for                               |
| -------------------------------- | -------------------------------------- |
| Incomplete transfer              | 24 h after last progress               |
| Completed staged input           | 7 days                                 |
| Trashed Graphic Asset            | 30 days, restorable                    |
| Unreferenced superseded revision | 90 days                                |
| Unreachable content (quarantine) | 7 days, then rechecked before deletion |
| Evidence ledger entries          | 1 year                                 |

- `GET /api/admin/graphics-assets/retention` lists every deadline being held.
  `POST` runs a sweep now (safe any time; use it to drain a backlog).
- `GET …/evidence` is the audit trail. Successful sweeps log nothing else.
- `POST …/<assetId>/purge` with `{"confirmation":"purge-now"}` is the only way to
  reclaim Trash early.

Content deletion is two-phase (claim, delete bytes, recheck, drop the row), so
an outage never strands bytes without a catalogue record. A crashed claim
becomes reclaimable after a one-hour lease. Content that becomes reachable
mid-delete is marked Unavailable Graphic Asset Content with a
`content-deletion-conflict` entry: a repair case, not data loss.

**Unreleased staged input.** If the staging store is down when an ingestion
completes, is cancelled, is permanently rejected, or has its staged input
expire, that outcome stands, but its staged bytes stay counted against the
staging allowance. Every sweep retries the release indefinitely, and the
**Unreleased staged input** queue has a **Retry release** action. A warning
alert stands until the release lands, which records `staged-input-released`.

**Orphaned multipart uploads.** An in-flight multipart upload whose operation
row no longer exists is invisible to the sweep. Find and abort it with R2's S3
API:

```bash
aws s3api list-multipart-uploads --bucket stream-graphics-asset-staging \
  --endpoint-url https://<accountid>.r2.cloudflarestorage.com
aws s3api abort-multipart-upload --bucket stream-graphics-asset-staging \
  --key <key> --upload-id <UploadId> --endpoint-url https://<accountid>.r2.cloudflarestorage.com
```

### Reconciliation

Compares what the catalogue expects against what the canonical R2 bucket holds.
It never creates, redirects, or removes an asset, revision, or reference, so a
missed run only delays detection.

- **D1 is authoritative for what should be reachable; the byte store for which
  bytes exist.** `graphic_asset_contents.availability` is advisory:
  reconciliation is its only writer, and readers never trust it. A reader that
  sees the store answer and disagree reconciles that content immediately.
- **Each pass:** checks expectations least-recently-compared first; missing
  source bytes → Unavailable Graphic Asset Content (retryable, identities
  intact); missing derivative → regenerable discrepancy; size/type/digest
  mismatch → isolated **critical integrity incident**. It then scans one page of
  the store from a persisted cursor (a few thousand objects a day). Unexpected
  digest-owned keys go to 7-day quarantine and are never adopted. Non-digest
  keys become critical incidents and are never auto-deleted. Finally it reclaims
  stale repair/regeneration working copies.
- **Actions** (`/api/admin/graphics-assets/discrepancies/<id>`): `recheck`,
  `verify-stored-bytes` (full re-hash; the only way to detect same-size
  corruption, and the only action on an isolated incident),
  `regenerate-derivative` (must reproduce the recorded bytes exactly), and
  `PUT …/repair` with the exact original bytes (checked for length, SHA-256,
  validation, and recorded facts). There is no adopt action.
- **Isolated critical incidents are never repaired automatically.** Resolving a
  digest-key conflict is an operator decision.
- **Known limits:** deep verification only runs on an open discrepancy, so silent
  corruption behind agreeing metadata is detectable but not discovered. A
  verification immediately followed by a new incident on the same content is a
  race with retention deletion, not a new fault.

### Operations cockpit

`/admin/graphics-assets` reads `GET /api/admin/graphics-assets/operations-cockpit`:
one snapshot composed from durable state. Its size is bounded (counts, plus at
most 20 unfinished ingestion operations and 20 recent Evidence entries), and
each reading issues the same fixed set of D1 statements whatever the library
holds. Those are aggregates or bounded samples (the recent outcome is counted
over at most 200 Evidence entries), but the aggregates scan their tables, so a
reading's cost still grows with the catalogue; no latency limit is measured or
promised. It reports the catalogue and the canonical byte store as separate
conditions (`degraded` or `unavailable`) and still answers with
`outcome: catalogue-unavailable` when D1 is down.

- Severities: `critical` (cannot be trusted until someone acts), `warning` (a
  guarantee is at risk or an incident is retryable), `info`. Persistent alerts
  are backed by durable records and clear only when the incident does.
- Canonical quota boundaries: warning 80%, critical 95%, blocked 100%. The
  staging allowance is a separate budget.
- Actions: run reconciliation, run retention. Capacity limits are changed on
  `/admin/graphics-assets/health`; purge, repair, and verification stay on
  their own surfaces.

### Remote HTTPS copy

An author can copy a remote file into the library once, through the same
ingestion, validation, and publication path as an upload. Nothing keeps a link
to the remote host. The fetcher (`server/modules/graphics-asset-library/remote-source.ts`)
enforces at the first URL and at every redirect:

- public HTTPS only, no userinfo, only an `accept` header sent;
- at most three redirects, followed manually;
- every resolved A/AAAA record public (private, loopback, link-local, metadata,
  and embedded-IPv4 ranges rejected, Teredo rejected outright; `localhost`,
  `.local`, `.internal` refused before lookup);
- a transfer bounded by the kind's byte limit, at most one 16 MiB part resident.

Remote `Content-Type`, filename, and digest are ignored; the library derives
everything from the bytes. The URL is treated as a secret: it is never persisted,
logged, or stored in the browser, and errors show at most `scheme://host`. A
retry before any bytes are staged asks for the URL again. After server
validation the operation pauses at `awaiting-confirmation` for the browser to
decode the staged bytes and submit evidence.

DNS rebinding is mitigated, not prevented. Workers cannot pin `fetch` to a
resolved address or report the peer IP, so the resolver check (Cloudflare DoH)
is best-effort. Cloudflare's own subrequest restrictions are defence in depth.
A residual gap remains: a multipart upload is orphaned if the catalogue write
and the abort both fail in one attempt (see
[orphaned multipart uploads](#retention)).

### Silent-video validator

Silent-video publication requires server-side validation. Browsers only observe;
they cannot submit playback claims. The validator is a private Worker,
`stream-silent-video-validator` (`workers/silent-video-validator/`), reached
only through the `SILENT_VIDEO_PLAYBACK_VALIDATOR` service binding (no
`workers.dev` or preview URLs).

- Each validation idempotency key maps to one `silent-video-validation`
  Workflow instance. The Workflow re-verifies the staged object and streams it
  into a scale-to-zero Container. The Container is digest-pinned, uses Debian
  snapshot tooling, and has no network access. It proves complete decode, muted
  playback, seeks, and VP9-alpha transparency (ffprobe, ffmpeg, headless
  Chromium), and renders a deterministic transparent PNG poster fitted to
  640×360.
- Busy Containers answer 409 and the Workflow step retries. A validation
  reserves its Container before any asynchronous work and releases it only
  once its own workspace is cleaned up, whichever way it ends, so an
  overlapping request is always answered busy (#698). Durable state holds
  facts only, never bytes.
- Posters land under `validation/silent-video/` in the staging bucket. A
  30-day lifecycle rule, `silent-video-validation-posters`, created once with
  `wrangler r2 bucket lifecycle add`, reclaims them.
- An instance that ends errored or terminated is never restarted automatically.
  Fix the cause, then run
  `wrangler workflows instances restart silent-video-validation <id>`.
- The validator has its own TypeScript program
  (`workers/silent-video-validator/tsconfig.json`), standalone from the app's.
  Its runtime and binding types are `worker-configuration.d.ts` beside it,
  generated from its `wrangler.jsonc` by `pnpm types:validator` and committed.
  Like the app's root file (`pnpm types:app`), it is checked fresh:
  `pnpm typecheck:validator` (inside `pnpm typecheck`) fails when that file is
  stale or the Worker does not compile, and
  `pnpm validator:dry-run` bundles it as `pnpm deploy:validator` would without
  building the Container image (#618).
- Deploying needs Docker plus Workflows and Containers enabled on the account.
  Fixtures live in `scripts/silent-video-validator-fixtures.json`.
- Its acceptance gate's preflight, evidence and cleanup (#619) are proved
  locally against a fake Wrangler adapter
  (`test/unit/scripts/silentVideoValidatorAcceptance.test.ts`). What is still
  owed is one human-authorized deployed run: with the Deploy day variables set,
  `pnpm accept silent-video-validator --deployed` prints its one pass line with
  `cleaned=6`, leaves no cleanup manifest, and leaves no
  `ingestion/acceptance-*` object in the staging bucket; the same run with
  `STREAM_KEEPR_BROWSER_ACCEPTANCE_URL` set to another host, or with
  `CLOUDFLARE_ACCOUNT_ID` unset, stops before any Wrangler command runs.

## Graphics notes

- **Feature Match Overlay runs on the Shared Graphics Foundation.** The legacy
  widget / widget-group / z-index model was deleted without a migration.
  `test/unit/shared/featureMatchOverlayCapabilityParity.test.ts` pins every
  legacy capability against the recreated built-in presets (`full-table`,
  `left-stacked-player-cams`, `neon-feature-match`). Dropped by design: per-side
  borders on a Surface Style (compose with rule-preset Shape items), the
  `visible` text-overflow option, and per-child offsets and clamps.
- **The Deck List Graphic Item renders only in Feature Match Overlay.** Broadcast
  Graphics has no feature-match context and no deck data source, so the palette
  withholds it (ADR-0015). No built-in preset places one.
